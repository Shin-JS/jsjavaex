# ECR No: 기존 CA 생성 백엔드에 적용할 채번 코드

2026-10-20 기준입니다. 기존 CA 생성 처리에서 **name을 결정하는 호출부를 수정**하기 위한 Java 코드와 적용 조각입니다. 별도 생성 REST API·위젯·채번 스키마를 만들지 않습니다. 배포 서버의 OOTB Java/JPO 원본을 확보한 상태는 아니므로, 특정 벤더 파일을 직접 수정한 패치나 적용 완료본으로 표현하지 않습니다.

## 확정 규칙

`ECR-` + 사업부 1자리 + `yyMMdd` 6자리 + 순번 4자리 = 15자리. 저장 대상은 business object의 **name**입니다.

| 사업부 | 코드 | 첫 번호 예시 |
|---|---|---|
| MX | W | ECR-W2610200001 |
| NW | N | ECR-N2610200001 |
| VD | V | ECR-V2610200001 |
| DA | A | ECR-A2610200001 |
| HME | H | ECR-H2610200001 |

| 내부 정수 순번 | 표시 순번 |
|---:|---|
| 1 | 0001 |
| 9999 | 9999 |
| 10000 | A001 |
| 10998 | A999 |
| 10999 | B001 |
| 34975 | Z001 |
| 35973 | Z999 |
| 35974 이상 | 오류, 생성 중단 |

`A000`~`Z000`은 발급하지 않습니다. DB에는 계속 정수 순번을 저장하며 화면 번호만 변환합니다. `% 10000`이나 문자열 끝 네 자리 자르기를 사용하지 않습니다.

**구현 가정:** 사업부·날짜별 독립 순번, 매일 0001 시작, 한국 시간 기준입니다. 사용자가 확정한 사항은 번호 형식과 사업부 매핑 및 알파벳 전환입니다. 날짜별 초기화·사업부별 독립 여부는 아직 별도 확인되지 않은 가정입니다. 기존 업무 규칙이 다르면 이 가정부터 조정해야 합니다.

## 구성

- `EcrNumberRule.java`: 사업부 변환, 15자리 조립, 정수↔순번 변환.
- `EcrNameService.java`: 날짜를 한 번만 확정하고 기존 영속 채번기를 호출.
- `EnoviaNumberGeneratorSequence.java`: 기존 Number Generator 객체의 다음 순번 속성에 대해 트랜잭션 잠금→조회→검증→증가 수행.
- `PropertiesCounterResolver.java`: 기존 사업부·날짜별 카운터 ID의 명시적 매핑. 동일 객체의 여러 시리즈 재사용과 누락을 거부.
- [INTEGRATION.md](INTEGRATION.md): 기존 소스의 교체 지점과 코드 조각.
- [REFERENCES.md](REFERENCES.md): 실제 조회 자료와 확인 한계.
- [VALIDATION.md](VALIDATION.md): 검사 범위와 미검증 항목.

## 기존 소스 수정의 범위

원래의 CA 생성 서비스, 인증·권한 검사, 트랜잭션, 객체 생성 호출, 분류 저장, 응답 처리를 유지합니다. 대상 커스텀 타입의 **최종 이름 발급 분기**에서 이 코드를 호출하고 결과를 기존 생성 호출의 name에 전달합니다. 기본 CA와 다른 타입의 기존 이름 발급 분기는 유지합니다.

새 utility 클래스가 추가되지만 새로운 업무 생성 API나 위젯을 만드는 방식은 아닙니다. utility를 둘 수 없는 배포라면 해당 메서드를 기존 커스텀 Java/JPO 내부로 옮겨 사용할 수 있습니다. 실제 타입의 대소문자와 정확한 생성 메서드명은 설치 소스로 확인해야 합니다.

## 기존 카운터 연결

기존 채번이 이미 영속적이고 원자적인 정수 순번을 반환한다면 `EcrNameService.ExistingSequence`에 그 호출을 연결하는 것이 우선입니다. 이 경우 ENOVIA 어댑터와 properties resolver는 필요 없습니다.

기존 ENOVIA Number Generator 객체를 직접 사용하는 경우에는 속성명이 실제 환경에서 `eService Next Number`인지 확인하고 전달합니다. 이 값은 **다음에 발급할 정수**여야 합니다. 마지막 발급값을 저장하는 기존 구현이면 의미를 그대로 혼용하지 말고 연결부를 수정합니다.

`counter-bindings.example.properties`는 설정 형식 예시이며 실행 가능한 운영 ID가 없습니다. 기존 카운터 ID로 채우고 서버의 기존 설정 로딩 경로로 읽습니다. 한 사업부·날짜에는 한 카운터만, 모든 서버 노드에서는 동일한 매핑을 사용합니다. 해당 카운터에 다른 OOTB 채번기가 동시에 값을 쓰면 안 됩니다. 기존 쓰기 경로까지 같은 잠금·증가 규약으로 통일해야 합니다.

**객체 ID·매핑·실제 생성 호출부 연결은 아직 완료되지 않았습니다.** 날짜에 맞는 기존 카운터가 없으면 코드는 생성을 거부합니다. 카운터를 자동 생성하거나 공용 카운터를 1로 리셋하지 않습니다. 기존 시스템이 일자별 카운터를 제공하지 않는다면 기존 영속 채번 구현에서 날짜별 시리즈를 지원하도록 수정해야 하며, 이 자료만으로 매일 자동 초기화가 완성된다고 볼 수 없습니다.

기존 발급번호가 있는 날짜는 1로 재설정하지 않습니다. 예를 들어 마지막 번호가 A999이면 다음 정수값은 10999입니다. 기존 객체 전체와 기존 채번 이력을 확인해 시작값을 이관해야 하며, 검색 색인의 마지막 번호만 보고 초기화하지 않습니다.

## 트랜잭션과 동시성

ENOVIA 어댑터는 기존 **update 트랜잭션 안에서만** 실행됩니다. 기존 트랜잭션을 별도 commit/abort하지 않습니다. 카운터의 `lockForUpdate` 후 속성을 읽고, Z999 초과를 검사한 다음 증가시킵니다. CA 생성과 분류 저장까지 성공한 뒤 기존 호출자가 commit합니다. 실패 시 기존 호출자는 전체 트랜잭션을 abort해야 합니다. 예외를 잡고 계속 생성하면 안 됩니다.

현재 날짜는 잠금 대기 전에 한 번 확정합니다. 자정에 걸친 요청은 해당 확정 날짜를 일관되게 사용합니다. 클라이언트 요청의 날짜·사업부 문자열을 그대로 신뢰하지 말고 기존 서버에서 검증한 생성 조직/업무 속성으로 사업부를 결정합니다. SecurityContext 문자열을 임의로 분해해 사업부로 추측하는 코드는 포함하지 않았습니다.

실제 분산 잠금 및 롤백 동작은 설치 버전·DB에서 검증해야 합니다. 순번 할당 후 응답을 잃고 사용자가 다시 요청하는 경우의 중복 생성 방지는 원래 생성 서비스의 재요청 처리 범위입니다.

## 검사 실행

JDK 17에서 Java 8 호환 대상으로 컴파일합니다.

```bash
python3 run_tests.py
```

실제 빌드는 `src`만 설치 환경 ENOVIA JAR를 classpath에 넣어 수행합니다. **tests/stubs는 배포하거나 실제 ENOVIA JAR와 함께 컴파일하지 않습니다.** 이 저장소의 검사는 대역 API를 사용하며 서버 통합 검사와 구분됩니다.
