# 기존 ECR 번호 조회와 다음 번호 결정

## 실제 MQL

생성일이 2026-10-20, 사업부가 MX(W)일 때 조회는 다음과 같습니다.

```mql
temp query bus * ECR-W261020* * vault * select name dump |;
```

Java 구현은 명령에 값을 이어 붙이지 않고 인자를 바인딩합니다.

```java
String result = MQLCommand.exec(context,
    "temp query bus $1 $2 $3 vault $4 select name dump $5",
    Arrays.asList(typePattern, prefix + "*", "*", vaultPattern, "|"));
```

코드: `src/com/sdx/enovia/ecr/MqlExistingEcrNumbers.java`. 검색 색인의 마지막 번호가 아니라 business object의 현재 name을 조회합니다. MQL 실행 오류는 예외로 전달하며 0001을 대신 발급하지 않습니다.

## 마지막 순번 계산

`temp query bus ... select name dump |`의 한 행은 `type|name|revision|name`으로 해석합니다. 출력 형식이 다르면 생성하지 않고 오류를 냅니다. 같은 사업부·날짜의 15자리 번호만 대상으로 삼습니다. 길이가 다른 이름은 이번 번호 규칙의 대상에서 제외하고, 15자리인데 A000/0000 등 잘못된 순번이 있으면 자동 추정하지 않고 실패시킵니다.

순번은 `EcrNumberRule.ordinal()`로 정수에 대응시킨 후 최대값을 구합니다. 조회 결과가 정렬돼 있다고 가정하지 않습니다. 같은 이름의 여러 리비전은 최대값 계산 결과를 바꾸지 않습니다.

| 조회된 마지막 번호 | 저장된 다음 순번 | 이번 발급 | 저장할 다음 순번 |
|---|---:|---|---:|
| 없음 | 빈 값 또는 0 | ECR-W2610200001 | 2 |
| ECR-W2610200010 | 1 | ECR-W2610200011 | 12 |
| ECR-W2610209999 | 1 | ECR-W261020A001 | 10001 |
| ECR-W261020A999 | 1 | ECR-W261020B001 | 11000 |
| ECR-W2610200001 | 20000 | 정수 20000에 해당하는 번호 | 20001 |
| ECR-W261020Z999 | 1 | 생성 거부 | 변경 없음 |

## 실행 순서

1. 기존 CA 생성 update 트랜잭션인지 검사합니다.
2. 해당 사업부·날짜의 기존 카운터 객체에 `lockForUpdate`를 잡습니다.
3. 카운터의 다음 순번을 읽습니다.
4. 동일 Context에서 MQL로 기존 ECR name을 조회하고 최대 순번을 계산합니다.
5. `next = max(1, counterNext, existingMax + 1)`을 계산합니다.
6. 최대값 35973(Z999)을 넘으면 중단합니다.
7. 카운터에 `next + 1`을 저장하고 `CreateParameters.name`에 발급번호를 설정합니다.
8. 원래 CA 생성과 후속 처리가 성공하면 기존 호출자가 commit합니다. 실패하면 전체를 abort합니다.

잠금은 조회 전에 취득하고, 이 코드가 임의로 commit하거나 unlock하지 않습니다. 같은 시리즈의 요청은 같은 카운터를 사용해야 하며 모든 WAS가 같은 설정을 사용해야 합니다. 이 방식 밖에서 같은 번호를 직접 생성하는 경로까지 자동으로 동기화되는 것은 아닙니다.

## 카운터를 유지하는 이유와 범위

기존 객체만 조회한 뒤 +1 하면 동시 요청이 같은 최대값을 볼 수 있습니다. 카운터 객체는 공통 잠금 기준이자 이미 발급한 다음 값의 저장소입니다. 현재 조회 결과가 줄어도 저장값보다 뒤로 돌아가지 않습니다. 한 트랜잭션에서 객체를 만들기 전 여러 번호를 먼저 예약하는 경우도 저장값을 따라 증가합니다.

이 코드의 적용 이전에 삭제됐고 카운터에도 기록되지 않은 번호는 현재 객체 조회만으로 복원할 수 없습니다. 그런 과거 번호까지 재사용을 금지해야 하면 기존 발급 이력의 다음 값을 카운터에 이관해야 합니다.

카운터 객체를 자동 생성하는 코드는 아닙니다. 기존 날짜별 카운터 ID·사업부 매핑 설정은 여전히 필요합니다. 객체가 없을 때 잠금 없이 조회만 실행하는 우회는 하지 않습니다.

## 조회 범위와 검증 한계

기본 조회 범위는 모든 타입/모든 vault입니다. 범위를 제한하면 같은 번호 체계의 과거 타입·다른 vault가 빠지지 않는지 확인해야 합니다. 실제로 조회되는 객체는 실행 Context의 읽기 권한에 영향을 받습니다. 따라서 전체 번호 체계를 읽을 수 있는 기존 서버 실행 문맥을 사용해야 합니다. 코드가 권한을 임의로 올리지는 않습니다.

참조 SDK에 대한 컴파일, MQL 출력 대역과 호출 순서·발급 계산 검사는 통과했습니다. 실제 ENOVIA 서버의 MQL 실행, 전체 데이터 조회 범위, 다중 WAS 잠금과 롤백은 배포 환경에서 확인해야 합니다. 특히 설치 서버의 실제 MQL 출력 한 행이 위 파서 형식과 일치하는지 확인합니다.
