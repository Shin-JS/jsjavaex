# 기존 생성 소스의 수정 위치와 적용 조각

## 현재 확인된 위치와 확인되지 않은 위치

직전 대화의 `/authoring/createContent/Create`는 생성 흐름의 추적 후보입니다. `ChgUXServicesChangeAction_mxJPO`는 사용자 환경에서 실행이 확인됐지만, 확인된 것은 CA 조회 요청 경로이며 생성·채번 메서드라고 단정하지 않습니다. 공개 자료에서 현재 설치 버전의 생성 구현 전체는 확보하지 못했습니다.

따라서 이 문서는 실제 OOTB 파일에 대한 unified diff가 아닙니다. 아래 변수와 `original...` 호출은 **연결 위치를 보여주는 표기**입니다. 확인하지 않은 벤더 API 이름을 만들어 호출하지 않습니다.

## 1. 기존 name 생성 지점을 찾기

기존 생성 요청을 디버깅하여 name 변수가 확정되는 곳을 찾습니다. 소스 검색 후보는 `createContent`, `getAutoGeneratedName`, `autoName`, `createObject`입니다. 후보 문자열이 있다고 실제 호출된다는 뜻은 아니므로, 최종 객체 생성 직전 name과 호출 스택을 확인합니다.

현재 구현이 이름과 객체를 한 번에 만드는 API라면 객체 생성 뒤 rename하는 코드를 추가하지 않습니다. 해당 API의 내부 이름 결정 지점 또는 설치 버전이 제공하는 확장 지점에 같은 규칙을 연결합니다. 객체 생성 트리거에서 이름을 바꾸는 방식으로 임의 우회하지 않습니다.

## 2. 기존 채번기가 이미 정수값을 주는 경우

기존 update 트랜잭션 안에서, 대상 타입 분기의 기존 name 발급 호출만 다음 형태로 바꿉니다.

```java
// sType, verifiedDivision, sName은 기존 생성 메서드의 실제 변수에 대응합니다.
// configuredEcrType은 실제 설치된 커스텀 타입명. 대소문자를 임의 고정하지 않습니다.
if (configuredEcrType.equals(sType)) {
    sName = ecrNameService.nextName(verifiedDivision, (code, day, maximum) -> {
        // 이 한 줄을 기존 영속 채번 호출로 연결합니다.
        // 원자적 정수 발급, 사업부/날짜 시리즈, maximum 초과 차단을 지원해야 합니다.
        return originalAtomicSequenceReservation(code, day, maximum);
    });
} else {
    sName = originalNameAllocation(/* 기존 인자 유지 */);
}
// 이후 원래 객체 생성 호출에 sName 전달. 정책/리비전/소유자/권한/분류 처리는 유지.
```

이미 영속 채번이 없다면 위 이름만 가진 함수를 임의로 추가했다고 구현 완료가 되지 않습니다. 다음 ENOVIA 구현을 검토합니다.

## 3. 기존 ENOVIA Number Generator 객체에 연결하는 경우

서버 초기화 시 기존 설정에서 매핑을 읽습니다. 여기서는 `existingServerProperties`를 이미 읽은 설정이라고 표기합니다.

```java
PropertiesCounterResolver resolver = new PropertiesCounterResolver(existingServerProperties);
EcrNameService ecrNameService = new EcrNameService();
```

요청 처리 시 기존 Context와 현재 update 트랜잭션을 그대로 사용합니다. Context를 공용 서비스 필드에 저장하지 않습니다.

```java
if (configuredEcrType.equals(sType)) {
    EnoviaNumberGeneratorSequence sequence = new EnoviaNumberGeneratorSequence(
        context,
        resolver,
        "eService Next Number" // 실제 설치 환경의 기존 속성명 확인 필요
    );
    sName = ecrNameService.nextName(verifiedDivision, sequence);
} else {
    sName = originalNameAllocation(/* 기존 인자 유지 */);
}
// 원래 생성 호출의 name 인자에 sName 사용.
// 이 아래에서 기존 코드가 sName을 다시 autoname으로 덮어쓰지 않는지 확인.
```

기존 Object Generator의 Prefix를 요청마다 `ECR-W261020`처럼 바꾸지 않습니다. 공용 설정이 동시에 갱신되면 서로 다른 사업부의 요청이 섞일 수 있습니다. 원래 autoName 호출과 이 어댑터를 함께 실행하면 순번을 두 번 소비하므로, 대상 분기에서는 기존 발급 호출을 **교체**해야 합니다.

## 4. 원래 트랜잭션의 오류 처리를 유지

발급 실패, Z999 초과, 권한 오류, 생성·분류 저장 오류는 기존 오류 처리로 전달합니다. 기존 트랜잭션 소유자가 abort하고 요청을 실패시켜야 합니다. 어댑터 내부에서는 권한 상승, 트리거 끄기, 새 트랜잭션, 자동 재시도, 별도 commit을 수행하지 않습니다.

기존 번호의 허용 범위 검증이나 DB 제약이 숫자 네 자리만 허용한다면 A001도 허용하도록 해당 검증을 함께 수정해야 합니다. 카운터 속성은 정수 35974까지 저장할 수 있어야 하며, 번호 표시 필드만 네 자리입니다.

## 5. 실제 서버에서 확인할 항목

- 생성한 객체의 name이 15자리인지, Title만 바뀐 것은 아닌지.
- 대상 커스텀 타입에만 적용되는지, 실제 최종 생성 호출이 값을 다시 바꾸지 않는지.
- 같은 사업부·날짜의 동시 요청 및 서로 다른 WAS 노드에서 중복이 없는지.
- 9999→A001, A999→B001, Z999 이후 거부.
- 생성 실패 후 카운터와 객체의 전체 롤백, 잠금 해제.
- 두 사업부, 날짜 변경, 기존 카운터 누락과 접근 권한 오류.
- 카운터 ID의 업무 시리즈 매핑이 실제 데이터와 일치하는지. 코드의 Counter 값만 맞춘다고 실제 객체 소속이 검증되는 것은 아닙니다.

테스트에서는 SDK 대역만 사용했습니다. 위 항목은 운영 배포 전 설치 환경에서 확인해야 합니다.
