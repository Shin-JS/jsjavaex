# R2024x 기존 CA 생성 코드 수정

## 수정 대상

참조 저장소: Ignim94/R2024x, **master** 브랜치, 커밋 `ef1fd81959f127ec7d5d5760cf2178e381cf738a`.

실제 수정 지점은 `PLMJChangeActionImpl.jar` 안의 다음 클래스입니다.

```text
com.dassault_systemes.enovia.changeaction.newservices.ENONewChangeActionApplicationAdapter
    private BusinessObject createBusinessObject(Context, CreateParameters)
```

메서드 시작에 다음 호출을 추가합니다. 실제 로컬 변수명은 설치 소스를 따릅니다.

```java
com.sdx.enovia.ecr.SdxEcrNameHook.apply(context, createParameters);
```

이 위치는 기존 `createNewObject()`의 Business Logic 실행 및 소유자 검사 뒤에 호출됩니다. 이후 원래 `CreateParameters.create(context)`와 인터페이스 추가, RPE 정리, 생성 후 처리는 그대로 진행합니다. Hook은 `CreateParameters.setName()`에 번호를 넣으며 생성 후 rename하지 않습니다.

## 앞선 JPO 설명의 정정

`jpo/enoECMChangeActionBase_mxJPO.java`의 `createChangeAction()`은 Deprecated입니다. `DomainObject.getAutoGeneratedName(...)`은 **주석 안의 이전 코드**입니다. 활성 코드는 `new ChangeAction().create(context)`입니다. 따라서 그 주석을 수정하거나 주석 해제하는 패치는 만들지 않았습니다.

`enterprisechangemgt.jar`에서 해당 `ChangeAction.create(Context)`가 Factory에 null name을 전달하고, 구현부가 ENONew CA adapter를 사용함을 확인했습니다. 명시적 name을 전달하면 setEnforcedName으로 이어지는 경로도 있지만 이번 패치는 실제 생성 직전의 공통 지점을 사용합니다.

`ChgUXServicesChangeActionBase_mxJPO`의 createChangeAction은 Issues 앱용 전달 메서드입니다. 동일 저장소의 UX JAR에서는 그 정적 메서드가 확인되지 않아, JPO만 보고 현재 위젯의 생성 진입점으로 간주하지 않았습니다. 조회 경로에 디버거가 잡힌 사실과 생성 호출 경로를 구분합니다.

## 위젯 REST 경로와의 관계

`NewContentWebServices.jar`에서 ENONewServices.createObject → ENONewAdaptor.createObject → ENONewCreateObjectImpl.createNewObject → getLeadingAppImpl → CA adapter.createNewObject 구조를 확인했습니다. ENONewServices는 update 트랜잭션을 시작하며 실패 시 abort하는 처리를 갖습니다.

Leading app 선택은 기존 타입 매핑을 따릅니다. 현재 설치된 커스텀 타입이 이 CA adapter를 사용하는지는 서버 디버거에서 최종 확인해야 합니다. 이 패치로 새 REST API나 타입 매핑을 추가하지 않습니다.

## 기존 Java 소스에 적용

소스를 보유한 개발 환경에서 실행합니다.

```bash
python3 apply_r2024x_adapter_patch.py PATH/ENONewChangeActionApplicationAdapter.java
```

스크립트는 클래스명·private 메서드·인자 타입·예외 서명을 확인하고, 현재 변수명에 맞는 호출 한 줄을 삽입합니다. 원본은 `.pre-ecr.bak`에 보관합니다. 반복 적용은 변경하지 않습니다. 서명이 다르거나 이미 불일치한 수정이 있으면 중단합니다.

`patches/r2024x-ca-adapter.patch`는 조회한 JAR의 메서드 구조를 기준으로 만든 참고 diff입니다. JAR만 제공된 클래스이므로 복원된 식별자를 사용합니다. 정식 벤더 Java 원본 파일에 대해 생성한 diff라고 주장하지 않습니다. 자동 스크립트는 변수명을 캡처하므로 문서의 변수명에 맞추려고 기존 소스를 고칠 필요가 없습니다.

**제공한 것은 실제 메서드를 수정하는 패치와 컴파일 가능한 Hook입니다. 벤더 클래스 전체를 새로 작성하거나 JAR를 통째로 교체한 결과물은 아닙니다.** JAR만 있고 Java 개발 소스가 없는 환경이라면 설치 버전에 맞는 해당 클래스 개발 소스를 확보해야 합니다. 이 스크립트는 JAR를 역컴파일하거나 바이트코드를 자동 변조하지 않습니다.

## 배포 설정

1. `src`의 사용자 작성 Java를 기존 백엔드 빌드에 추가합니다.
2. 위 어댑터 메서드를 패치하고 기존 빌드 방식으로 컴파일합니다.
3. `sdx-ecr.example.properties`를 `sdx-ecr.properties`로 복사하고 기존 서버 classpath에 배포합니다. 실제 기존 카운터 ID와 사업부 매핑을 입력합니다.
4. 대상 타입 기본값은 대소문자를 구분하는 `sdxEcChangeAction`입니다. 실제 이름이 다르면 JVM 옵션 `-Dsdx.ecr.targetType=실제타입명`을 지정합니다.
5. 기존 서버 배포 방식으로 변경 클래스를 반영합니다.

새 attribute/type/policy/Number Generator 객체를 자동으로 만들지 않습니다. 원래 존재하는 영속 카운터에 연결하며, 매핑이 없으면 대상 타입의 생성을 실패시킵니다. 사업부·날짜별 카운터가 없는 환경에서 이 패치만으로 일자별 순번 초기화가 완성되는 것은 아닙니다.

사업부는 서버 `Context.getRole()`의 정확한 값에 대한 매핑을 먼저 보고, 없으면 서버 `Context.getUser()`의 매핑을 봅니다. Role 값에 조직이 포함된다고 임의 가정하거나 문자열을 분해하지 않습니다. 조직별 매핑이 필요하면 실제 인증된 credential 값을 확인해 그 값 전체를 매핑하거나 기존 서버의 검증된 조직 조회 코드를 연결해야 합니다. 클라이언트가 보낸 임의 사업부 값은 사용하지 않습니다.

기본 CA와 다른 타입은 설정 파일을 읽거나 카운터를 갱신하지 않습니다. 다만 같은 대상 커스텀 타입을 생성하는 다른 화면도 이 채번 규칙을 적용받습니다. 백엔드 타입 규칙이므로 위젯 ID에 의존하지 않습니다.

## 기존 번호 조회와 카운터 보정

실제 Hook이 `MqlExistingEcrNumbers`를 호출하도록 연결했습니다. 카운터의 `lockForUpdate` 뒤에 기존 번호를 조회하고, 그 결과와 저장값을 비교합니다. [EXISTING-NUMBERS.md](EXISTING-NUMBERS.md)에 MQL, 반환값 해석 및 경계값 예시를 적었습니다. CA adapter의 기존 삽입 한 줄은 그대로 사용합니다.

기본 조회 범위는 `typePattern=*`, `vaultPattern=*`입니다. `ecr.query.typePattern`/`ecr.query.vaultPattern`으로 변경할 수 있지만 같은 번호 체계를 사용하는 기존 객체를 빠뜨리면 안 됩니다. 조회 Context에는 해당 번호 체계 전체를 읽을 권한이 필요합니다. 조회 실패를 빈 결과로 취급하지 않으며, 코드가 임의로 권한을 올리지는 않습니다.

## 실제 SDK 컴파일 확인

```bash
python3 compile_with_sdk.py PATH/TO/WEB-INF/lib
```

R2024x 저장소의 `eMatrixServletRMI.jar`와 `NewContentWebServices.jar`로 사용자 작성 전체 소스의 컴파일을 확인했습니다. 테스트 대역을 포함하지 않은 검사입니다. 기존 카운터 갱신은 실제 SDK의 `BusinessObject.lockForUpdate`, `getAttributeValues`, `setAttributeValue`를 사용하도록 수정했습니다.

벤더 클래스 전체 및 서버와의 통합 빌드는 별도입니다. 실제 서버에서 커스텀 타입의 생성 진입, 권한, 원자성, 다중 WAS, 오류 롤백, 카운터 이관과 날짜별 준비 상태를 확인해야 합니다.
