# 사용자 정보에 따른 클래스 속성 자동 표시 검토

검토일: 2026-10-14

새 Change Action 생성 화면을 열 때 사용자 정보로 적용할 클래스를 결정하고, 검색창 없이 해당 클래스의 속성과 입력 필드를 속성 탭에 표시하는 방안입니다.

이 문서는 최초 가능성 검토 기록입니다. 이후 작성한 조직별 자동 적용 소스와 적용 방법은 [README](README.md)를 참고하세요. 기존 작업은 [ca-isolated-kit](../ca-isolated-kit/README.md)에 있으며, 이 문서는 그 코드의 확장 방향을 설명합니다.

## 가능성 판단

현재 구조를 확장하면 구현 가능할 것으로 보입니다. 사용자가 검색하거나 찾아보기로 클래스를 선택하는 과정을 코드가 자동으로 수행하고, 기존 분류 컨트롤러의 속성 모델과 입력 폼을 재사용하는 방향입니다.

이 판단은 기존 코드의 선택·폼 생성 연결 흐름을 근거로 합니다. 설치 환경에서 자동 선택과 필수값 검증, 실제 저장까지 확인한 결과는 아닙니다.

## 라이브러리와 클래스의 구분

현재 입력 필드로 표시하는 대상은 라이브러리 자체의 속성이 아니라 라이브러리 안에 있는 클래스의 분류 속성입니다.

사용자 정보로 특정 라이브러리를 결정하더라도, 그 안의 어떤 클래스를 적용할지 추가로 결정해야 합니다. 라이브러리에 여러 클래스가 있는 경우 첫 번째 클래스나 모든 클래스를 임의로 적용하면 안 됩니다.

기본 설계는 사용자 기준으로 한 개의 클래스 ID를 결정하는 것입니다. 여러 클래스 적용이 필요하면 매핑 결과와 선택 순서, 필수값을 별도로 정의해야 합니다.

## 화면 초기화 흐름

1. 대상 위젯 설정과 생성 타입을 검사하고 대화상자 전용 bridge를 만듭니다.
2. 로그인 사용자 정보를 조회하는 작업과 기존 분류 컨트롤러의 준비를 기다립니다.
3. 사용자·조직 등의 매핑 규칙으로 적용할 클래스 ID를 결정합니다.
4. 클래스 ID로 선택에 필요한 클래스 정보를 조회하고 노드를 구성합니다.
5. 기존 선택 경로에 그 노드를 전달하여 클래스를 자동 선택합니다.
6. 기존 분류 기능이 클래스 속성을 조회하고 입력 폼을 생성하도록 기다립니다.
7. 기존 move 처리로 폼을 속성 탭에 표시합니다. 사용자가 속성값을 입력합니다.
8. 생성 완료 시 기존 분류 연결·속성 저장 경로를 사용합니다.

사용자 조회와 컨트롤러 초기화는 독립적으로 진행할 수 있으나, 자동 선택은 두 작업과 클래스 정보 조회가 준비된 뒤 수행해야 합니다.

## 기존 코드에서 재사용할 부분

| 기존 함수·객체 | 현재 역할 | 자동 표시에서의 활용 |
|---|---|---|
| sdxECCAAttachBridge | 위젯·타입 검사와 facet 연결 | 적용 범위와 대화상자별 상태 유지 |
| sdxECCAGetCurrentUserParameters | 현재 로그인 사용자 조회 | 버튼 클릭 대신 화면 초기화에서 호출 |
| sdxECCAConnectClassificationFacet | 기존 컨트롤러 준비 확인 | 자동 선택을 시작할 준비 조건 |
| sdxECCALibraryAdapter.add | 클래스 노드를 기존 선택 모델에 추가 | 사용자의 선택 대신 프로그램에서 호출 |
| 기존 클래스 선택 change 처리 | 속성 모델과 폼 생성 | 속성 정의·입력 컨트롤 재사용 |
| sdxECCARenderClassFields | 기존 분류 폼을 속성 탭으로 이동 | move 단일 동작 유지 |
| 기존 postCreation | 생성된 객체의 분류 연결·속성 저장 | 기존 저장 경로 유지, 통합 확인 필요 |

sdxECCALibraryAdapter.add는 클래스 ID 문자열만 받는 함수가 아닙니다. getID(), getLabel(), plmType 등 기존 컨트롤러가 사용하는 정보를 갖춘 클래스 노드가 필요합니다.

add의 Promise 완료는 선택 반영을 뜻하며 클래스 속성 조회 완료나 서버 저장 완료를 뜻하지 않습니다. 자동 표시 준비 완료 판정에는 실제 속성 로딩 완료 조건을 별도로 연결해야 합니다.

## 추가 구현이 필요한 부분

### 사용자와 클래스의 매핑

어떤 사용자 정보로 어떤 클래스 ID를 선택할지 결정하는 규칙이 필요합니다. 계정명, 현재 선택한 조직, 역할 등이 후보이며 실제 업무 규칙은 아직 정하지 않았습니다.

매핑을 프런트 설정으로 둘지 서버의 기준정보/API로 관리할지도 결정해야 합니다. 라이브러리와 클래스 표시명은 중복될 수 있으므로 최종 선택은 ID 기준으로 처리합니다.

기존 사용자 조회 결과의 preferredCredentials는 사용자의 기본 권한 문맥입니다. 현재 생성 화면에서 선택한 securityContext와 일치한다고 가정하지 않습니다. 조직 기준이면 어느 문맥의 조직을 사용할지 먼저 정해야 합니다.

### 클래스 ID로 노드 구성

현재 검색 경로는 검색 응답으로 선택 노드를 만듭니다. 자동 적용에서는 지정한 클래스 ID로 해당 클래스의 타입·제목·선택에 필요한 정보를 조회하는 경로가 추가로 필요합니다.

설치 버전에서 사용할 조회 서비스와 응답 형태를 확인해야 합니다. 정확한 조회 API와 새 노드 생성 코드는 이 검토에서 확정하지 않았습니다.

### 초기화 시점으로 사용자 조회 이동

현재 사용자 조회는 커스텀 수신 함수가 연결된 찾아보기 버튼 클릭 경로에 있습니다. 검색창과 버튼을 제거하면 이 경로가 실행되지 않습니다.

자동 표시에서는 사용자 조회 함수를 화면 초기화에서 명시적으로 호출하고, 컨트롤러 준비와 합류시켜야 합니다. sdxECCAOpenClassSelector는 버튼용 연결 함수이므로 자동 적용의 필수 경로로 삼을 필요가 없습니다.

### 화면 표시와 준비 상태

검색 입력창과 찾아보기 버튼의 표시·생성을 생략하고, 속성 폼 영역과 로딩·오류 메시지는 유지합니다. 기존 분류 컨트롤러와 선택 모델은 자동 선택과 저장에 필요하므로 제거하지 않습니다.

폼 표시 로직을 검색 UI 생성 함수에서 분리해야 검색 UI를 만들지 않고도 폼 영역과 bridge 구독을 구성할 수 있습니다. 기존 분류 탭의 라이브러리 선택 영역 숨김도 대상 bridge가 있는 화면에만 적용합니다.

사용자 조회, 클래스 적용, 필수 속성 준비가 끝나기 전에 생성하지 않도록 기존 생성 버튼·검증 경로에 준비 상태를 반영해야 합니다. 이 연결 지점은 설치 소스에서 확인해야 합니다.

### 중복 실행과 종료 처리

bridge 구독은 준비·선택 변경 때 여러 번 호출됩니다. 대화상자별 적용 중/완료 상태를 관리하여 같은 클래스를 반복 추가하지 않아야 합니다.

화면을 닫은 뒤 도착한 사용자·클래스 조회 응답은 무시하고, 기존 종료 처리로 폼을 복원합니다. 자동 적용 상태를 공용 모듈의 전역 변수에 두지 않습니다.

## 실패와 문맥 변경 시 결정할 동작

사용자 조회 실패, 매핑 없음, 매핑 중복, 클래스 조회 실패, 접근 권한 부족, 속성 로딩 실패를 구분해야 합니다. 검색창이 없으므로 실패 시 사용자가 직접 다른 클래스를 선택해 해결할 수 없습니다. 메시지와 재시도 또는 생성 제한 정책을 정해야 합니다.

생성 화면에서 타입이나 securityContext가 바뀔 수 있다면 자동 적용 규칙을 다시 평가할지도 결정해야 합니다. 이미 입력한 값을 초기화하거나 다른 클래스에 옮기는 처리는 임의로 수행하지 않습니다.

사용자 정보로 클래스를 자동 선택하는 것과 속성값을 자동으로 채우는 것은 별개입니다. 이번 검토 범위는 클래스 속성 정의와 입력 필드를 자동 표시하는 것입니다.

## 다른 위젯과 저장에 미치는 영향

기존 위젯 활성화 설정과 타입 조건을 함께 유지하고, 자동 적용도 그 조건을 통과한 대화상자에서만 수행합니다. 공용 HTML에서 모든 위젯에 활성화 값을 지정하지 않습니다.

기존 폼과 모델을 재사용하여 기존 저장 경로를 활용하는 방향입니다. 다만 자동 선택 이후 분류 연결, 필수 속성 검증, 입력값 커밋, 실제 속성 저장이 모두 이어지는지는 설치 환경에서 확인해야 합니다.

## 구현 전 확인할 항목

- 사용자 판단 기준과 사용자/조직별 클래스 ID 매핑.
- 특정 라이브러리 안에서 한 클래스 또는 여러 클래스를 적용할지 여부.
- 현재 사용자 API 응답과 클래스 ID 조회 서비스.
- 클래스 속성 로딩 완료를 알 수 있는 이벤트나 상태.
- 자동 적용 실패 시 재시도·생성 제한 동작.
- 생성 화면의 타입·권한 문맥 변경을 허용할지 여부.
- 대상 위젯의 표시·검증·저장과 다른 위젯의 기존 동작.
